# 段階B設計メモ: ユーザー写真の共有(公式画像の置き換え)

作成: 2026-09-06 / 状態: **設計案・未着手**(判断が必要な項目は末尾)

## 目的

- 公式画像への依存を段階的に外し、権利者からの一括削除要請を受けてもアプリの価値が残る構造にする
- 競合ガチャログと同じ「みんなで作る図鑑」を、**メーカー横断の自動カタログ(事実データ)を土台に**して差別化する。ガチャログはシリーズ自体をユーザーが登録するが、本アプリは14,000件超のシリーズ・ラインナップ名が最初から揃っており、ユーザーは「写真を足すだけ」で済む
- A層(SNSに戦利品を撮って投稿する層)の行動をそのままアプリ内の貢献に変える

## 現状との差分

| 観点 | 現状(段階A) | 段階B |
|---|---|---|
| サーバー | なし | 必要(画像ストレージ・DB・関数) |
| ユーザー識別 | なし | 匿名ID(端末生成、サインイン不要)。バックアップ/復元で引き継ぐ |
| データセーフティ | 収集なし | 「写真(ユーザー生成コンテンツ)」「匿名ID」を申告 |
| プライバシーポリシー・利用規約 | 端末内保存のみを記載 | 投稿ライセンス、モデレーション、削除手続きを追記 |
| Google Playポリシー | 通常アプリ | **UGCポリシー**適用: 利用規約への同意、アプリ内の通報、投稿者ブロック、モデレーション体制、違反者への対処 |
| コスト | 0円 | 月数百〜数千円(下記) |

## 機能仕様

### 投稿

- 対象: **アイテム単位**(シリーズのメイン画像は、採用済みアイテム写真から自動で選ぶ/合成する)
- 導線: 既存の「自分の写真」登録時に「みんなの図鑑にも使う」トグル(デフォルトON、初回のみ説明ダイアログ)。端末内保存と共有をひとつの操作にする
- 送信するもの: 画像(長辺1200px・JPEG・EXIF除去)、アイテムID、匿名ID、投稿日時。位置情報は送らない
- 端末側で行うこと: 正方形トリミングUI(公式画像が正方形なので統一)、EXIF除去、リサイズ

### 判定と採用(4段階)

1. **自動判定**(投稿直後、サーバー関数)
   - 不適切画像: SafeSearch系API(成人向け・暴力・人物の顔を検出したら保留)
   - 一致度: 画像と「シリーズ名 + アイテム名」のテキストをマルチモーダルモデルで照合し0〜1のスコア。公式画像との類似度も参考値として算出(公式画像は保存せず判定時に参照のみ)
   - 画質: 解像度・ブレ(ラプラシアン分散)・明度・被写体の占有率
   - 結果: `auto_score`。閾値未満は「保留」、明確な違反は「拒否」
2. **投稿者本人だけに表示**(pending)。自分の端末では即座に自分の写真が使われる(現状と同じ)
3. **コミュニティ承認**: そのシリーズを開いた他ユーザーに「この写真は正しい?」を1タップで聞く。**3人の承認**(ガチャログと同じ基準)で採用。通報が1件でも入れば保留に戻す
4. **採用(approved)**: 全ユーザーに配信。採用写真はCDN経由

### ブラッシュアップ(差し替え)

- 採用写真にも「いいね」を持たせ、`quality = auto_score × 0.5 + いいね正規化 × 0.5` で順位付け
- 新しい投稿が現行を上回り、かつ承認条件を満たしたら差し替え。旧写真は履歴として保持(ロールバック・投稿者クレジット維持)
- 1アイテムあたり最大5枚を保持、6枚目以降は最下位を破棄

### 投稿者へのインセンティブ

- 採用写真に投稿者名(任意のニックネーム、未設定なら「ガチャ活ユーザー」)
- 実績: 「図鑑職人」(採用1枚)、「図鑑の匠」(採用20枚)、「シリーズ完成」(1シリーズ全アイテムの採用写真が自分)
- シェアカードに「この写真は○○さん提供」を入れられる

### 荒らし・愉快犯対策

- 匿名IDごとの投稿レート制限(1日20枚)、初回投稿から7日間は1日5枚
- 通報3件で自動保留、運営確認まで非表示
- 通報された投稿者は承認に必要な人数が増える(3→5)。繰り返しで投稿禁止(匿名IDをブロックリストへ)
- 承認の重み: 承認者自身の採用実績が多いほど重み増(自演の複数端末承認を薄める)
- 運営用の簡易管理画面(保留一覧・拒否・ブロック)。当面はSupabaseのテーブルエディタでも代替可

### 権利処理

- 利用規約: 「投稿写真を本アプリ内で表示・トリミング・合成・配信する非独占的・無償のライセンスを運営者に付与。投稿者は自身が撮影した写真のみ投稿できる」
- 権利者向け窓口(既存)に「投稿写真」も含める。申し出があればシリーズ/メーカー単位で非表示(既存の `ImagePolicy` の仕組みを投稿写真にも適用)
- 投稿者本人の削除要求は即時反映(ストレージから物理削除)

## アーキテクチャ案

```
アプリ(Flutter)
  ├─ 匿名ID(初回起動時にUUID生成、SharedPreferences、バックアップに含める)
  ├─ 投稿: 端末でリサイズ/EXIF除去 → Storage に直接アップロード → photos テーブルに行を追加
  ├─ 表示: 採用写真URL(CDN) → GachaImage の優先順位を  自分の写真 → 採用写真 → 公式画像 → プレースホルダー  に変更
  └─ 承認/通報/いいね: RPC 1本ずつ

バックエンド(Supabase 想定)
  ├─ Postgres: photos(id, item_id, series_id, maker, poster_id, status, auto_score, likes, created_at)
  │            approvals(photo_id, voter_id) / reports(photo_id, reporter_id, reason)
  │            posters(id, nickname, approved_count, blocked)
  ├─ Storage: photos/{status}/{photo_id}.jpg (pending は非公開バケット、approved は公開バケット+CDN)
  ├─ Edge Function: on-upload → 自動判定(SafeSearch + マルチモーダル) → status 更新
  ├─ RLS: 自分の pending だけ読める / approved は全員読める / 書き込みは自分の行のみ
  └─ 配信用スナップショット: approved の {item_id: url} を1時間ごとにJSONへ書き出し、
     既存の gacha_data.json と同じ方式(GitHub raw or Storage)で配布 → アプリ起動時に1回取得すれば済み、DB読み取りが増えない
```

### なぜSupabaseか(Firebaseとの比較)

| | Supabase | Firebase |
|---|---|---|
| DB | Postgres(SQLで集計・順位付けが楽) | Firestore(集計はCloud Functionsで自前) |
| 匿名認証 | あり | あり |
| ストレージ+CDN | あり(公開バケット) | あり |
| 無料枠 | DB 500MB / Storage 1GB / 帯域 5GB | Storage 5GB / 帯域 1GB/日 |
| 有料の目安 | $25/月(Pro) | 従量 |
| 管理画面 | テーブルエディタで保留一覧をそのまま運用できる | コンソールはやや不便 |
| 判断 | **第一候補**。写真1枚150KB×採用2万枚=3GB程度でPro必須になる見込み。それでも月$25+判定API数ドル | 代替 |

判定APIの費用: 投稿1枚あたり SafeSearch 約0.15円 + マルチモーダル照合 約0.3〜1円。月1万投稿でも数千円〜1万円。

## 移行計画

1. **B-0(準備)**: 利用規約・プライバシーポリシー改定案、データセーフティ回答の更新、Supabaseプロジェクト作成(本番/検証)
2. **B-1(投稿と自分だけの表示)**: 匿名ID、アップロード、pending表示。サーバーには載るが他人には見えない → ポリシー要件のうち通報・ブロックを先に実装
3. **B-2(自動判定+承認+配信)**: Edge Function、承認UI、スナップショット配信、GachaImageの優先順位変更
4. **B-3(差し替え・実績・クレジット)**: いいね、順位付け、実績3種、シェアカードのクレジット
5. 採用写真がシリーズの一定割合に達したメーカーから、公式画像をデフォルト非表示に切り替え(`hide_official_images`)
